# ระบบที่ปรึกษาด้านภาษีด้วยปัญญาประดิษฐ์บนไลน์ โดยใช้ระบบอัตโนมัติ

Development of an AI-Based Tax Advisory System on LINE Using Workflow Automation

ปริญญานิพนธ์ระดับปริญญาตรี ภาควิชาวิทยาการคอมพิวเตอร์และเทคโนโลยีสารสนเทศ
คณะวิทยาศาสตร์ มหาวิทยาลัยนเรศวร

ผู้จัดทำ นายยศกร แจ้งมณี และนางสาวณัฏฐณิชา ป้องป้อม
อาจารย์ที่ปรึกษา ผู้ช่วยศาสตราจารย์ ดร.สัญญา เครือหงษ์

## ระบบนี้คืออะไร

แชตบอตใน LINE ที่ตอบคำถามภาษีเงินได้บุคคลธรรมดา พิมพ์ถามเหมือนคุยกับคน
ตอบกลับพร้อมบอกว่าอ้างอิงกฎหมายมาตราไหน

```
คุณ : เงินเดือน 50,000 บาทต่อเดือน ประกันสังคม 9,000 บาท ต้องเสียภาษีเท่าไหร่

บอท : ภาษีที่ต้องชำระคือ 20,600 บาทค่ะ 📊
      เงินได้ทั้งปี 600,000 บาท
      หักค่าใช้จ่าย 100,000 บาท
      หักลดหย่อนส่วนตัว 60,000 บาท และประกันสังคม 9,000 บาท
      เงินได้สุทธิคงเหลือ 431,000 บาท
      ภาษีที่ต้องชำระ 20,600 บาท
```

ถามได้ทั้งการคำนวณภาษี ค่าลดหย่อนแต่ละอย่าง กำหนดยื่นและแบบที่ต้องใช้
ค่าปรับเมื่อยื่นช้า และขอให้ยกถ้อยคำของมาตราที่ต้องการมาดู

**สิ่งที่ต่างจากการถาม ChatGPT** คือตัวเลขทุกตัวมาจาก deterministic code ที่มี unit test กำกับ
ไม่ใช่ LLM คิดเอง ถามคำถามเดิมสิบครั้งได้คำตอบเดิมทุกครั้ง
สถาปัตยกรรมเป็นแบบ RAG คือค้นข้อมูลจริงจาก knowledge base ก่อน แล้วให้ LLM ตอบจากข้อมูลนั้น

วัดจากคำถาม 155 ข้อที่อ้างอิงกฎหมายจริง รันสามรอบเป็น 465 ครั้ง Gemini ตอบถูกทุกครั้ง
ตัวเลขนี้ตีความอย่างไรอยู่ในหัวข้อ [ผลการทดลอง](#ผลการทดลอง) ซึ่งอธิบายไว้ด้วยว่า
ทำไมคะแนนเต็มร้อยไม่ได้แปลว่าระบบไม่มีข้อบกพร่อง

## ศัพท์ที่ควรรู้

เอกสารนี้เป็นภาษาไทย แต่ศัพท์เทคนิคทุกคำมีคำมาตรฐานภาษาอังกฤษกำกับไว้เสมอ

| คำไทยในเอกสารนี้ | ศัพท์มาตรฐาน | ความหมายในระบบนี้ |
|---|---|---|
| แบบจำลองภาษา | **LLM** | Gemini 3.1 Flash Lite เข้าใจคำถามและเรียบเรียงคำตอบ |
| คำสั่งระบบ | **system prompt** | ข้อความกำหนดบทบาทและกฎให้ LLM ส่งไปทุกครั้งที่เรียก |
| ข้อมูลนำเข้า | **context** | ทุกอย่างที่ส่งเข้า LLM ในหนึ่งครั้ง รวมคำถามและผลการค้น |
| งบบริบท | **context budget** | ขนาดสูงสุดของผลการค้นที่ยัดเข้า context ระบบนี้ตั้ง 3,000 ตัวอักษร |
| ฐานข้อมูล | **knowledge base** | ตาราง `tax_law_knowledge` 104 รายการที่ใช้ตอบคำถาม |
| การสืบค้น | **retrieval** | ดึงรายการจากฐานข้อมูลมาแนบเข้า context |
| จับคู่คำสำคัญ | **keyword matching** | วิธี retrieval ของระบบนี้ ใช้แทน vector search |
| สถาปัตยกรรมโดยรวม | **RAG** | ค้นข้อมูลจริงก่อน แล้วให้ LLM ตอบจากข้อมูลนั้น ไม่ตอบจากความจำล้วน |
| เครื่องมือ | **tool** / **function calling** | ฟังก์ชันที่ LLM เรียกใช้ได้ เช่น เครื่องคำนวณภาษี |
| ด่านตรวจ | **guardrail** | กฎที่บังคับในโค้ด ไม่ใช่ขอให้ LLM ทำตาม |
| การจำแนกประเภทคำถาม | **intent classification** | ตัดสินว่าคำถามเป็นประเภทไหน ทำด้วยกฎ ไม่ใช้ LLM |
| ตอบมั่วโดยดูน่าเชื่อ | **hallucination** | ความเสี่ยงหลักของงานนี้ แก้ด้วยการบังคับเรียก tool และแนบมาตรา |
| ตาข่ายรองรับ | **fallback** | ทางสำรอง เช่น สลับไป Push API เมื่อ reply token หมดอายุ |
| ลายนิ้วมือ | **fingerprint** | ค่าแฮชของโค้ดและข้อมูล ใช้ตัดสินว่าผลวัดเดิมยังใช้ได้ไหม |
| เวลาตอบช้าที่สุด P95 | **p95 latency** | ค่าที่ 95% ของคำขอเร็วกว่านี้ ทนค่าผิดปกติได้ดีกว่าค่าเฉลี่ย |
| ความยินยอม | **consent** | สถานะตาม PDPA ว่าผู้ใช้ยอมให้เก็บข้อมูลหรือไม่ |

## ติดตั้งและใช้งาน

ฉบับย่อสำหรับคนที่คุ้นกับ Docker และบรรทัดคำสั่งอยู่แล้ว
คู่มือฉบับละเอียดสำหรับคนที่ไม่เคยเขียนโปรแกรมมีอยู่ แต่ไม่ได้เผยแพร่ใน repository นี้

**ต้องติดตั้ง** Docker Desktop, Node.js 20+, Python 3.10+
**ต้องสมัคร** (ฟรีทั้งหมด ไม่ต้องใช้บัตรเครดิต) — บัญชี Google เพื่อขอ API key ของ Gemini
ที่ [aistudio.google.com/apikey](https://aistudio.google.com/apikey) · บัญชี
[ngrok](https://dashboard.ngrok.com/signup) · LINE Official Account ที่เปิด Messaging API แล้ว

### 1 ดาวน์โหลดและตั้งค่า

```bash
git clone https://github.com/cchiOru/Tax_legal_final_version.git
cd Tax_legal_final_version
cp .env.example .env
```

เปิด `.env` แล้วแทนที่ค่าตัวอย่าง 6 บรรทัดนี้ บรรทัดอื่นปล่อยไว้ได้

```
POSTGRES_PASSWORD=ตั้งรหัสผ่านฐานข้อมูลเอง
N8N_ENCRYPTION_KEY=ข้อความสุ่ม 32 ตัวอักษร
NGROK_AUTHTOKEN=ค่าที่ได้จาก ngrok
LINE_CHANNEL_ACCESS_TOKEN=ค่าที่ได้จาก LINE Developers
LINE_CHANNEL_SECRET=ค่าที่ได้จาก LINE Developers
GEMINI_API_KEY=ค่าที่ได้จาก Google AI Studio
```

`.env` ไม่อยู่ใน repository เพราะเก็บรหัสลับ **ห้ามอัปโหลดขึ้นที่สาธารณะเด็ดขาด**

### 2 เปิดระบบ

```bash
docker compose up -d
docker compose ps
```

ต้องขึ้นครบ 4 ตัวและมีสถานะ running หรือ healthy — `tax-advisor-postgres`, `tax-advisor-n8n`,
`tax-advisor-ngrok`, `tax-advisor-admin`
ถ้าตัวไหน exited ให้ดูสาเหตุด้วย `docker compose logs ชื่อตัวนั้น`

> pgadmin เป็นบริการเสริมสำหรับดูฐานข้อมูลผ่านหน้าเว็บ ตั้ง `profiles: tools` ไว้จึงไม่ขึ้นตามปกติ
> ถ้าต้องการใช้ให้สั่ง `docker compose --profile tools up -d` แล้วเปิด http://localhost:5050

### 3 ใส่ความรู้เรื่องกฎหมายภาษี

```bash
for f in seed-tax-law seed-tax-law-extra seed-tax-law-full \
         seed-tax-law-cases seed-tax-forms seed-tax-law-deductions-detail \
         seed-tax-law-exempt-and-freelance seed-tax-law-social-security \
         seed-tax-law-modern-income; do
  docker cp postgres/$f.sql tax-advisor-postgres:/tmp/
  docker exec tax-advisor-postgres psql -U n8n_admin -d tax_advisor -f /tmp/$f.sql
done

for m in postgres/migrations/*.sql; do
  docker cp $m tax-advisor-postgres:/tmp/m.sql
  docker exec tax-advisor-postgres psql -U n8n_admin -d tax_advisor -f /tmp/m.sql
done
```

ตรวจว่าเข้าครบ ต้องได้ **104** จากนั้นดึงตัวบทประมวลรัษฎากรฉบับปัจจุบันจากเว็บกรมสรรพากร
ใช้เวลาราวหนึ่งนาที จะได้ไฟล์ `seed-revenue-code-current.sql` แล้วนำเข้าแบบเดียวกับข้างบน

```bash
docker exec tax-advisor-postgres psql -U n8n_admin -d tax_advisor \
  -c "SELECT count(*) FROM tax_law_knowledge;"

pip install requests beautifulsoup4
python postgres/import-revenue-code-current.py
```

### 4 สร้างและนำเข้าเวิร์กโฟลว์

```bash
python n8n/build-workflow.py
```

จะได้ `n8n/workflows/tax-advisor-workflow.json` จากนั้นเปิด http://localhost:5678
สร้างบัญชีผู้ดูแล กด **Import from File** เลือกไฟล์นั้น ผูก credential ให้ครบ
(PostgreSQL 8 โหนด, Google Gemini 1 โหนด) แล้วกดสวิตช์ **Active** ให้เป็นสีเขียว

ค่าที่ใช้ผูก credential ของ PostgreSQL — Host `postgres` · Database `tax_advisor` ·
User `n8n_admin` · Port `5432` · Password ใช้ค่าเดียวกับ `POSTGRES_PASSWORD` ใน `.env`

> Host ต้องเป็น `postgres` ไม่ใช่ `localhost` เพราะ n8n มองหาฐานข้อมูลจากในเครือข่ายของ Docker

**ผูก credential ครั้งเดียวพอ** หลังผูกเสร็จ ไปที่เมนู Credentials คลิก credential
แล้วคัดลอกรหัสจากแถบที่อยู่ (`.../credentials/AbCdEf123456` ส่วนท้ายคือรหัส)
ใส่ลงใน `.env` ที่ `N8N_PG_CREDENTIAL_ID` และ `N8N_LLM_CREDENTIAL_ID`
ครั้งต่อไปที่รัน `build-workflow.py` ไฟล์จะผูก credential มาให้เลย นำเข้าแล้วกด Active ได้ทันที

## ที่มาของโครงงาน

คนจำนวนมากไม่รู้ว่าตัวเองต้องยื่นภาษีหรือไม่ ต้องเสียเท่าไร และลดหย่อนอะไรได้บ้าง
ช่องทางที่มีอยู่ยังตอบไม่ครบ — เว็บกรมสรรพากรมีข้อมูลครบแต่เป็นภาษากฎหมาย
สายด่วน 1161 ตอบตรงจุดแต่จำกัดเวลาราชการ สำนักงานบัญชีตอบดีที่สุดแต่มีค่าใช้จ่าย
ส่วนแชตบอต AI ทั่วไปตอบทันทีและอ่านง่าย **แต่ตัวเลขเชื่อไม่ได้และตรวจสอบที่มาไม่ได้**
ข้อสุดท้ายคือสิ่งที่โครงงานนี้ต้องการแก้

### แนวคิดของระบบ

LLM คำนวณผิดได้โดยที่ยังอ้างมาตราถูกต้อง ผู้ใช้จึงไม่มีทางรู้ว่าคำตอบผิด
ตัวอย่างที่พบระหว่างพัฒนาคือมันอ้างมาตรา 47(1)(ง) ได้ถูก แต่ลืมหักค่าใช้จ่าย 100,000 บาท
และลืมค่าลดหย่อนส่วนตัว 60,000 บาท โครงงานนี้จึงแยกงานเป็นสองส่วน
**ส่วนที่ต้องถูกต้องแน่นอนเขียนเป็น deterministic code ที่มี unit test กำกับ
ส่วนที่ต้องยืดหยุ่นจึงปล่อยให้ LLM ทำ**

| หน้าที่ | ใครทำ | ตรวจสอบอย่างไร |
|---|---|---|
| เข้าใจคำถามภาษาไทยที่ผู้ใช้พิมพ์ | LLM | ชุดคำถามทดสอบ 155 ข้อ |
| คำนวณภาษี เงินเพิ่ม ค่าปรับ | deterministic code | `test-tax-calculator` 90 ข้อ |
| หาเนื้อหากฎหมายที่เกี่ยวข้อง | retrieval ด้วย keyword matching | `test-retrieval` 22 ข้อ |
| เรียบเรียงให้คนทั่วไปอ่านรู้เรื่อง | LLM | วัดความยาวและรูปแบบคำตอบ |
| บังคับรูปแบบคำตอบและด่านตัวเลข | guardrail ในโค้ด | `test-reply-guard` 60 ข้อ |
| ไม่เก็บข้อมูลคนที่ไม่ยินยอม | โครงสร้าง workflow | `test-consent-guard` 23 ข้อ |

ชุดทดสอบทั้งหมด **305 ข้อ** ทุกข้ออ่านโค้ดและไฟล์เวิร์กโฟลว์ที่ใช้งานจริงมาตรวจโดยตรง
ไม่ได้คัดลอกโค้ดมาทดสอบซ้ำ และไม่เรียกบริการภายนอกเลย จึงรันได้ทุกครั้งที่แก้ระบบ

`test-retrieval` มีไว้แยกสาเหตุเวลาตอบผิด ว่าเป็น **retrieval failure** คือค้นไม่เจอ
(แก้ที่ knowledge base หรือวิธีค้น) หรือ **generation failure** คือค้นเจอแล้วแต่ตอบไม่ครบ
(แก้ที่ system prompt) การเรียก LLM จริงบอกได้แค่ว่าผิด แต่ไม่บอกว่าผิดที่ขั้นตอนไหน

## ผลการทดลอง

### ข้อค้นพบหลัก สั่งด้วย prompt อย่างเดียวไม่พอ

ตอนแรกเขียนกฎลงใน system prompt ทั้งหมด ผลคือ LLM ทำตามบ้างไม่ทำตามบ้าง
เมื่อย้ายกฎเดียวกันไปบังคับด้วยโค้ด ผลดีขึ้นชัดเจน

> **สิ่งที่ต้องรับประกันได้ ห้ามฝากไว้กับ prompt ต้องบังคับใน deterministic code เท่านั้น**
>
> นี่คือข้อค้นพบหลักของโครงงาน

| ตัวชี้วัด | สั่งด้วย system prompt | บังคับด้วย guardrail |
|---|---|---|
| เรียก tool เมื่อโจทย์ต้องใช้ตัวเลข | 79.5% | 94.9% |
| มีคำเตือนแสดงให้ผู้ใช้เห็น | ขาดเป็นบางครั้ง | 100% |
| ความยาวคำตอบเฉลี่ย | 729 ตัวอักษร | 404 ตัวอักษร |

ตารางนี้เป็นการเปรียบเทียบแบบควบคุมตัวแปร ใช้ชุดคำถามและ knowledge base ชุดเดียวกัน
เปลี่ยนเฉพาะวิธีบังคับ จึงไม่ใช่ตัวเลขล่าสุดของระบบ

ยังพบด้วยว่า **system prompt ยิ่งยาว LLM ยิ่งทำตามน้อยลง** ซึ่งสวนกับที่คาดไว้ตอนแรก
คือที่ความยาว 2,275 / 3,321 / 4,017 ตัวอักษร จำนวนครั้งที่ไม่เรียก tool เป็น 2 / 3 / 8 ตามลำดับ
จึงเขียน system prompt ใหม่ให้สั้นลงและย้ายกฎสำคัญที่สุดไปไว้ต้นข้อความ
สอดคล้องกับปรากฏการณ์ **lost in the middle** คือเนื้อหากลาง prompt ถูกให้น้ำหนักน้อยที่สุด

### ความแม่นยำโดยรวม

วัดจากคำถาม 155 ข้อ ทุกข้ออ้างอิงตัวบทกฎหมายจริง รันสามรอบเป็น 465 ครั้ง
วัดสองแบบจำลองด้วยระบบเดียวกัน knowledge base ชุดเดียวกัน คำสั่งชุดเดียวกัน
ต่างกันเฉพาะ LLM (วัดเมื่อ 11 และ 13 กันยายน 2569)

|---|---|---|---|

| เรียก tool เมื่อต้องใช้ | 100% | 92.6% | 98% |
| ตัวเลขถูกในข้อที่มีตัวเลข | 100% | 86.7% | — |
| ค้นเจอข้อมูลอ้างอิง | 100% | 100% | ≥ 90% |
| latency มัธยฐาน | **3.2 วินาที** | 21.8 วินาที | — |
| latency p95 | **6.7 วินาที** | 61.4 วินาที | — |
| ตอบเกิน 20 วินาที | **0 จาก 465** | 245 จาก 465 | 0 |

Gemini ผ่านครบทุกเกณฑ์ ส่วน Typhoon ผ่านสองในสาม ติดที่ความเร็ว
Typhoon ถูกใช้เป็นตัวชี้วัดระหว่างพัฒนาเพราะรันในเครื่องและไม่มีโควตาจำกัด
จึงรันซ้ำได้ทุกครั้งที่แก้ระบบ ต่างจาก Gemini ที่โควตาฟรีจำกัดต่อวัน

### ข้อควรระวังในการตีความเลข 100 เปอร์เซ็นต์

ตัวเลขนี้แปลว่า **ชุดคำถามแยกความสามารถของ Gemini ไม่ออกแล้ว** ไม่ได้แปลว่าระบบไม่มีข้อผิดพลาด
และมีหลักฐานยืนยันชัดเจนจากประวัติการพัฒนา

ชุดคำถามนี้เคยได้ 100% บนฐานข้อมูล 87 รายการ พอขยายเป็น 97 แล้ววัดใหม่ คะแนนตกเหลือ 99.4%
การไล่หาสาเหตุทำให้พบบั๊กจริงสองตัวที่ตอนได้ 100% ซ่อนอยู่โดยไม่มีใครเห็น

- **บั๊ก retrieval** วิธีคุม context budget เดิมตัดรายการท้ายสุดออกทีละรายการ
  รายการที่มีคำตอบอยู่อันดับสาม แต่อันดับสองยาวผิดปกติจึงเบียดจนอันดับสามถูกตัดก่อน
- **บั๊ก intent classification** คำถาม "อายุ 65 ปีขึ้นไปได้รับยกเว้นเงินได้เท่าไหร่"
  ถูกจัดเป็นคำถามคำนวณเพราะมีคำว่าเท่าไหร่และมีตัวเลข ทั้งที่ 65 คืออายุไม่ใช่จำนวนเงิน
  ข้อนี้ตอบถูก แต่ถูกเพราะแบบจำลองรู้คำตอบเอง ไม่ใช่เพราะระบบค้นมาให้
  **เป็นการผ่านโดยบังเอิญ ซึ่งอันตรายกว่าการตอบผิดเพราะมองไม่เห็น**

ข้อสรุปเชิงวิธีวิจัยคือ คะแนนเต็มร้อยไม่ได้แปลว่าไม่มีข้อบกพร่อง แต่แปลว่าเครื่องมือวัดมองไม่เห็น
การที่คะแนนลดลงชั่วคราวเมื่อขยายขอบเขตการวัด จึงเป็นสัญญาณว่าเครื่องมือวัดเริ่มทำงาน ไม่ใช่ระบบแย่ลง
ข้อสังเกตนี้ยืนยันอีกครั้งเมื่อขยายชุดคำถามจาก 115 เป็น 155 ข้อแล้ว Gemini ยังได้ 100% เท่าเดิม
การวัดต่อจากนี้จึงต้องทดสอบกับผู้ใช้จริง

## สถาปัตยกรรม

```
ผู้ใช้ (แอป LINE)  →  LINE Messaging API + Rich Menu 6 ปุ่ม  →  ngrok  →  n8n Workflow 41 โหนด

 1. แยกเหตุการณ์จาก LINE
      ├─ กดเพิ่มเพื่อน → ขอความยินยอมเก็บข้อมูลก่อนเริ่มใช้งาน
      ├─ กดปุ่มตอบ     → บันทึกความยินยอม แล้วแสดงคำเตือนการใช้งานครั้งเดียว
      ├─ กดปุ่ม postback → บันทึกรายงานปัญหาจากผู้ใช้
      └─ พิมพ์ข้อความ  → เข้าสู่การตอบคำถามด้านล่าง
 2. ดักคำสั่งจัดการข้อมูลของตัวเอง เช่น ลบข้อมูลของฉัน
 3. ดักคำทักทายและปุ่มเมนู ตอบด้วยข้อความสำเร็จรูปโดยไม่เรียก LLM
 4. ดึงโปรไฟล์ผู้ใช้จาก LINE แล้วบันทึกลง PostgreSQL
 5. retrieval จาก knowledge base ด้วย keyword matching 382 คู่
 6. intent classification ด้วยกฎ ถ้าต้องได้ตัวเลขจะแนบคำสั่งบังคับเรียก tool
 7. แยกเส้นทางตาม consent
      ├─ granted → AI Agent ที่ต่อ conversation memory และบันทึกบทสนทนา
      └─ denied  → AI Agent ที่ไม่ต่อ memory และไม่บันทึกอะไรเลย
 8. AI Agent
      ├─ LLM: Gemini 3.1 Flash Lite
      ├─ tool: คำนวณภาษีเงินได้บุคคลธรรมดา  (มีด่านตรวจ 4 ชั้นก่อนคำนวณ)
      ├─ tool: คำนวณเงินเพิ่มและค่าปรับ
      └─ tool: ค้นตัวบทประมวลรัษฎากร 309 มาตรา
 9. post-processing ก่อนส่งออก
      ├─ ลบ Markdown ทิ้ง เพราะ LINE ไม่ render
      ├─ ด่านตัวเลข ตรวจว่าเลขในคำตอบตรงกับผลเครื่องคำนวณ
      └─ ตัดความยาวที่ขอบบรรทัด ไม่ให้ผู้ใช้ต้องกด "ดูเพิ่มเติม"
10. เลือกช่องทางส่งตาม latency ที่วัดได้
      ├─ < 50 วินาที → Reply API ซึ่งใช้ฟรีไม่จำกัด
      └─ ≥ 50 วินาที → Push API เพราะ reply token หมดอายุแล้ว
11. บันทึกบทสนทนา เฉพาะผู้ใช้ที่ยินยอมเท่านั้น
```

**ด่านตรวจ 4 ชั้นก่อนคำนวณ** ทุกด่านปฏิเสธไม่คำนวณให้เลยเมื่อพบปัญหา ไม่ส่งตัวเลขกลับไปพร้อมคำเตือน
เพราะวัดแล้วพบว่าคำเตือนที่แนบไปพร้อมตัวเลขถูกเมิน 3 จาก 3 รอบ แต่การไม่ให้ตัวเลขเลย
ทำให้แบบจำลองยอมเรียกเครื่องมือใหม่ทันที

1. **คีย์วางผิดชั้น** เช่น ส่ง `spouse` ไว้ชั้นบนสุดแทนที่จะอยู่ใน `allowances` — ค่าลดหย่อนจะหาย ภาษีสูงเกินจริง
2. **ค่าผิดชนิด** เช่น ส่ง `income.profession` เป็นข้อความ — `Number()` อ่านไม่ออกจึงเป็น 0 เงียบ ๆ เงินได้หาย ภาษีต่ำเกินจริง
3. **ประเภทเงินได้ขัดแย้งกัน** เช่น ระบุว่าเป็นวิชาชีพแพทย์แต่ไม่มีเงินได้ในช่องวิชาชีพ
4. **ที่มาของค่าลดหย่อน** ตัดค่าลดหย่อนที่ผู้ใช้ไม่ได้เอ่ยถึงออก กันแบบจำลองเติมตัวเลขเอง

### ทำไมไม่ใช้ vector search

ทดลองแล้วใช้ไม่ได้ ภาษาไทยเขียนติดกันโดยไม่มีช่องว่างระหว่างคำ (no word delimiter)
PostgreSQL Full-Text Search ทำ tokenization ไม่ได้ วัดจากข้อมูลจริงแล้ว retrieval hit rate เป็นศูนย์
จึงเปลี่ยนมาใช้ domain-specific keyword matching ที่สร้างขึ้นเอง 382 คู่ แล้วได้ hit rate 100%

นี่เป็นข้อจำกัดของภาษาไทยที่งานภาษาอังกฤษไม่เจอ และเป็นผลการทดลองที่รายงานไว้ในบทที่ 4

## ข้อจำกัดของระบบ

**ยังไม่เคยทดสอบกับผู้ใช้จริง** ตัวเลขความแม่นยำวัดจากคำถาม 155 ข้อที่ผู้จัดทำสร้างขึ้นเอง
คำถามจากผู้ใช้จริงมักกำกวมและมีบริบทเฉพาะตัวมากกว่า ข้อจำกัดนี้ไม่ใช่การคาดเดา —
ตอนที่ชุดคำถามได้ 100% การลองพิมพ์ถามด้วยมือเพียงไม่กี่คำถามกลับพบข้อบกพร่อง 4 จุด
ที่ชุดคำถามจับไม่ได้เลย ทั้งหมดเกิดจากการถามต่อเนื่องหลายจังหวะและการใช้ภาษาแบบที่คนพิมพ์จริง
ชุดทดสอบจึงถูกขยายจาก 86 เป็น 305 ข้อเพื่อปิดช่องโหว่เหล่านั้น

**ขอบเขตจำกัดเฉพาะภาษีเงินได้บุคคลธรรมดา ปีภาษี 2567** ยังไม่รองรับภาษีเงินได้นิติบุคคล
และภาษีมูลค่าเพิ่มอย่างเต็มรูปแบบ

**พึ่งบริการภายนอกที่ควบคุมโควตาไม่ได้** ระหว่างวัดผลพบว่าโควตาฟรีของรุ่นที่เป็น preview
หมดตั้งแต่คำถามข้อที่ห้า ทั้งที่เอกสารระบุว่าให้ 1,500 คำขอต่อวัน
การนำไปใช้จริงกับผู้ใช้จำนวนมากจึงต้องประเมินค่าใช้จ่ายส่วนนี้ก่อน

**แบบจำลองที่รันในเครื่องยังตอบช้ากว่าเกณฑ์** การ์ดจอที่ใช้พัฒนามีหน่วยความจำ 4 GB
